# cxtodo → InfoBoard 待办联动手册（AI agent 执行版）

**一句话**：这份文档是给 AI agent 用的执行手册，用来把本机 `cxtodo`（学习通待办采集器）采到的待办单向同步进 InfoBoard 的 `todo.json`；人类也可以照着手动跑，所有命令都是可直接复制的。

- **方向**：单向 `cxtodo → InfoBoard`。cxtodo 里消失的条目（交了 / 过期 / 整门课被忽略 / 标了已处理），在 InfoBoard 里也删掉。
- **中间层是 AI**：没有内置定时钩子，也没有后台守护进程。AI 跑命令、看数据、自己组装 payload、自己决策、自己汇报。
- **依赖版本**：本机已装 `infoboard-todo` **0.12.0**，`apply` 子命令可用且**已实测跑通**（详见附录）。`apply` 自 0.12.0 起才有；0.11.0 上跑 `apply` 会得到 `未知命令：apply`（退出码 1）—— 这一句**本轮未复验**（本机已升级到 0.12.0，无从验证旧版行为）。

## 1. 触发语

用户说出下面这类话时，走本套流程：

- "同步学习通待办 / 把学习通作业同步进来"
- "联动一下 / 跑一下联动"
- "看看学习通有什么作业 / 学习通还有什么没交"

⚠️ **注意区分**："看看学习通有什么" ≠ "刷新学习通数据"。默认**只读本地快照**，不联网（见第 3 节）。

## 3. 铁律：默认只读，不要主动 `sync`

**AI 默认绝对不要主动跑 `sync`。** `sync` 会真的联网采集：

| 命令             | 耗时  | 说明                                      |
| ---------------- | ----- | ----------------------------------------- |
| `sync --pending` | ~20 s | 只重读还有未完成的学科                    |
| `sync -c <学科>` | ~10 s | 只重读一门课                              |
| `sync`（无参数） | ~80 s | 完整采集                                  |
| `sync --fast`    | 快    | 作业/考试全用缓存，**发现不了新交的作业** |

**只有用户明确说"刷新 / 重新采集 / 重新读一遍学习通"时**才跑 `sync`，并且必须在汇报里写明：`本次触发了采集，耗时 N 秒（模式：pending）`。

### 3.1 一个必须知道的副作用

`cxtodo list` **在没有快照时会自动触发一次 `sync --pending`**（约 20 秒，会真的联网）。实现上等价于：

```python
if refresh or view.load() is None:
    _sync("pending")      # 没有 state.json 就联网
```

所以：**有快照（`data\state.json` 存在）时 `list` 是纯本地只读，0.5 秒内返回**；快照不存在时第一次 `list` 会卡 20 秒。在自动化脚本里要预料到这个停顿，别误判成卡死并重试。

### 3.2 快照有多旧：先看再问

快照年龄有两个来源：

- `C:\Users\30993\Desktop\cxtodo\data\state.json` 里的 `synced_at`（形如 `2026-11-05T19:21:03`，本地时间）；
- `python run.py list`（**人类可读模式**）末尾那一行页脚：`数据更新于 N 分钟前（…）`。

⚠️ `list --json` **不打印页脚**（JSON 分支在打印页脚之前就 `return` 了），所以拿到 `--json` 输出后，年龄只能从 `state.json` 的 `synced_at` 算。

判定规则：

| 快照年龄    | 动作                                                                          |
| ----------- | ----------------------------------------------------------------------------- |
| ≤ 6 小时    | 直接同步，汇报里带上采集时间                                                  |
| 6 ~ 24 小时 | 可以同步，但汇报里提示"数据 N 小时前采集，要不要刷新？"                       |
| > 24 小时   | **先问用户**要不要刷新，得到确认再 `sync`；未确认就用旧数据同步并明确标注时间 |

## 4. 字段映射表

cxtodo `list --json` 的每一项 → InfoBoard `apply` payload 的 `items[]`：

| cxtodo 字段                                         | InfoBoard `items[]` | 规则                                                                                                                                                                                                                   |
| --------------------------------------------------- | ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                                                | `id`                | 加前缀 `cx-`，即 `f2602ce384` → `cx-f2602ce384`。**前缀就是安全边界**：`--prune cx-` 只会动这些条目                                                                                                                    |
| `course` + `title`                                  | `text`              | **`"{title_clean}｜{course}"`** —— **标题在前、课程在后**（全角竖线 U+FF5C）。`title_clean` = 先剥掉学习通自动加的 `^新建作业\d{10,}` 前缀。`kind == "考试"` 时末尾追加 `（考试）`；`kind == "互动"` 时追加 `（互动）` |
| `deadline`                                          | `deadline`          | **只取日期部分**：`2026-11-10T23:59:00` → `2026-11-10`。`null` → **整个字段省略**（不要写 `null`）                                                                                                                     |
| （无）                                              | `completed`         | cxtodo 侧恒为 `false`（`list` 已排除已处理条目）。但 `apply` 侧是**只升不降**：落盘值 = `已有.completed \|\| 本次.completed`，`true` 永不会被改回 `false`（详见下方 ⚠️）                                               |
| `stale`                                             | （无）              | `stale == true` 照常同步，但要在汇报里单独点出"有 N 条用的是旧缓存"                                                                                                                                                    |
| `source`                                            | （无）              | `source == "remain"` 表示截止时间是按平台"剩余 X 天"**推算**的，可能不准，要在汇报里单独点出                                                                                                                           |
| `status` / `bucket` / `first_seen` / `mark` / `new` | （无）              | 不参与同步，只用于汇报和判断                                                                                                                                                                                           |

**为什么是"标题在前、课程在后"（这条别改回去）**

实战踩过的坑：照 `"{course}｜{title}"` 拼，在 InfoBoard 主窗口（实测只有 **297px** 宽，文本区约 **119px** ≈ 9 个汉字就显示 `…`）里：

- 5 条 `微机原理实验｜新建作业20261031131621实验五 …` **全部显示成 `微机原理实验｜新…`，肉眼完全无法区分**；
- 2 条 `计算机辅助制造与工艺｜SW1.1…` / `SW1.2…` 也显示得一模一样。

三条理由：

1. **InfoBoard 是按字符从左往右截断的**，所以"能区分两条待办"的信息必须放在最左边；课程名只是归类信息，放后面被截掉不影响使用。
2. **`新建作业20261031131621` 是学习通自动生成的标题前缀**，那串 14 位时间戳对用户毫无意义，却在窄卡里把真正的内容全挤掉了 —— 所以在拼 `text` 之前先剥掉。
3. **实测对照**：改前 5 条微机原理实验在卡片上都是 `微机原理实验｜新…`；改后分别是 `实验五 基于CPU输入输出…` / `实验六 基于MCU输入输出…` 等，一眼可分辨。

顺带说明：InfoBoard 卡片和窗口的**每一行文本都带 `title` 属性**（鼠标悬停可看全文），所以截断**不丢信息**，只是不能"一眼分辨"。这也正是必须把区分信息放最左边的原因。

⚠️ **口径变更的副作用**：如果你已经用旧口径（课程在前）同步过，改成新口径后下一轮 `apply` 会显示 **`更新 11`**（`text` 变了），这是**预期行为**，不是数据损坏。

⚠️ **后缀分支的验证状态**：`（互动）` 分支**已实测**（科技写作与表达那条期末论文）；`（考试）` 分支**本轮未实测** —— 当前 11 条里没有未完成的考试（唯一那条考试早已被标 `done`，被 `list` 排除了），所以 `（考试）` 后缀目前只有代码逻辑保证。

**唯一的必填**：`items[].id` 和 `items[].text`。`deadline` / `completed` 都可能不传（省略 `completed` 等价于 `false`，对已有条目毫无影响，即不会取消勾选）。

> ⚠️ **`completed` 的真实语义是"只升不降"，而且升级不计入"更新"计数。**
> 落盘值为 `已有.completed || 本次.completed`，所以：
>
> - 对**已有**条目，payload 里写 `completed: true` **会**把未完成**升级成已完成并落盘**（`rev` 会 +1）—— 不是"只用于新建条目"；
> - 但**永远**不会把 `true` 改回 `false`（想取消勾选只能在 InfoBoard 里手动点，或者删掉重建）；
> - 这种"只升不降"的升级**不计入"更新"计数**：报告里可能仍然显示 `未变 1`，但 `（rev a → b）` 已经变了。
>
> 👉 **所以：判断"到底有没有写盘"，看 `rev` 有没有变，别只看"未变 N"这个计数。**

`list` 的默认过滤（已在 cxtodo 源码里确认）——所以拿到手的就是"现在还得做"的列表，**直接全量喂给 `apply` 即可**，不需要 AI 再做筛选：

- 整门课被忽略的学科（`data\config.json` 的 `ignore` 数组）
- 被标 `ignored` 的单条（`data\marks.json`）
- 被标 `done` 的单条（`data\marks.json`；加 `--all` 才会出现）

> 实测印证：`data\state.json` 里 `todo` 有 12 条，`list --json` 只输出 11 条 —— 少的正是 `marks.json` 里标了 `done` 的那条考试。

## 5. 标准执行序列

### 步骤 1：取快照（只读，不联网）

```powershell
$CX = 'C:\Users\30993\Desktop\cxtodo'
python "$CX\run.py" list --json > "$env:TEMP\cx-todo.json"
```

- 用绝对路径调 `run.py` 可以从任何目录跑（`run.py` 会自己把脚本目录塞进 `sys.path`，`data\` 仍指向 cxtodo 自己的目录）。
- 如果中文变乱码（旧控制台），先 `chcp 65001` 或 `$env:PYTHONIOENCODING='utf-8'`。
- PowerShell 7 下 `>` 重定向会写成 **UTF-8 无 BOM**，中文完好（已实测）。PowerShell 5.1 会写成 UTF-16，导致后续 JSON 解析失败 —— 那种环境请改用 `Out-File -Encoding utf8`。

### 步骤 2：转 payload（Python 写法，避开引号地狱）

把 cxtodo 的数组转成 `apply` 的 payload，并落盘到临时文件：

```powershell
$env:CX_LIST    = "$env:TEMP\cx-todo.json"
$env:CX_PAYLOAD = "$env:TEMP\infoboard-payload.json"

@'
import json, os, re
src = json.load(open(os.environ["CX_LIST"], encoding="utf-8-sig"))
out = []
for t in src:
    # 学习通自动加的"新建作业+14位时间戳"是纯噪音，且在窄卡片里会挤掉真正的内容
    title_clean = re.sub(r'^新建作业\d{10,}', '', t["title"]).strip()
    text = "%s｜%s" % (title_clean, t["course"])   # 标题在前、课程在后（截断时先丢课程，别丢标题）
    if t["kind"] == "考试":
        text += "（考试）"
    elif t["kind"] == "互动":
        text += "（互动）"
    d = {"id": "cx-" + t["id"], "text": text, "completed": False}
    if t.get("deadline"):
        d["deadline"] = t["deadline"][:10]
    out.append(d)
payload = {"items": out, "prune": ["cx-"]}
with open(os.environ["CX_PAYLOAD"], "w", encoding="utf-8") as f:
    json.dump(payload, f, ensure_ascii=False, indent=1)
print("payload ->", os.environ["CX_PAYLOAD"])
print("items =", len(out), " prune =", payload["prune"])
'@ | python -
```

- `encoding="utf-8-sig"` 是为了同时吃下"有 BOM / 无 BOM"两种 UTF-8。
- ⚠️ **`"prune": ["cx-"]` 必须带，漏掉会"静默失败"。** 没有 `prune`，`apply` 照样成功返回 0、`rev` 照样增长，但学习通里已经交掉的条目**永远不会从 InfoBoard 删掉** —— 表现为"列表越同步越长"，而错误很难被察觉。
- `prune` 有两个来源：payload 里的 `"prune": [...]`，和命令行 `--prune <前缀>`（可重复传多个）。二者取**并集** —— 可以两处都给、也可以只给一处，不会互相覆盖。本手册统一用 payload 里的 `prune`，一条命令就把"本次要管哪些前缀"说清楚。

> ⚠️ **不要用 PowerShell 重写这段转换逻辑。**
> `ConvertFrom-Json` 会把 ISO 时间字符串 `"2026-11-10T23:59:00"` **自动转成 `System.DateTime`**（实测类型就是 `System.DateTime`，跟参数无关），于是 `$_.deadline.Substring(0,10)` 直接炸：
>
> ```
> Method invocation failed because [System.DateTime] does not contain a method named 'Substring'.
> ```
>
> 而且 **`-AsHashtable` 也救不了**：本机 PowerShell 7.6.5 实测，加了 `-AsHashtable` 后 `deadline` 的类型**仍然是 `System.DateTime`**。
>
> 所以两条路：
>
> 1. **走 Python**（本文推荐，`t["deadline"][:10]` 天然是字符串切片）；
> 2. 非要用 PowerShell，就加 **`ConvertFrom-Json -DateKind String`**（PS 7.5+）保住原始字符串 —— 本机 7.6.5 实测：类型为 `System.String`，`Substring(0,10)` 得到 `2026-11-10`。

### 步骤 3：先 `--dry-run` 看差异（**不要跳过**）

```powershell
infoboard-todo apply --file "$env:TEMP\infoboard-payload.json" --dry-run
```

期望看到类似（这是**首次**同步的真实输出）：

```
读取 11 条：新增 11，更新 0，删除 0，未变 0（rev 18 不变）（dry-run，未写入）
```

⚠️ **`--dry-run` 不预演 `rev`**：它只显示**当前的** `rev` 值并标注 `不变`，不会写成 `rev a → b`。`rev a → b` 这种"变化"写法**只在正式写盘时出现**。所以别拿 dry-run 的输出判断"会不会涨 rev"。

用 `--json` 更好判断：

```powershell
infoboard-todo apply --file "$env:TEMP\infoboard-payload.json" --dry-run --json | ConvertFrom-Json |
  Select-Object rev, added, updated, removed, unchanged, dryRun
```

**停下来的条件**（差异不符合预期就不许正式 apply）：

- `removed` 大于"本来就应该消失的条数"（例如用户刚在 InfoBoard 里手写了几条 `cx-` 条目）；
- `added` 远大于 cxtodo 的条数（说明 payload 拼错了）；
- 出现 `updated` 而你预期是 0 —— 可能是 deadline 被"日粒度化"后反复抖动，先查清楚。
- **注意**：`--dry-run` 里 `rev` 永远是"当前值 不变"，所以上面这些计数就是你能拿到的全部信息；"`rev` 变了但计数全 0"的判据只适用于**正式 apply**（见步骤 4）。

### 步骤 4：正式 apply

用户已确认、或差异符合预期后：

```powershell
infoboard-todo apply --file "$env:TEMP\infoboard-payload.json"
```

想拿机器可读结果：

```powershell
infoboard-todo apply --file "$env:TEMP\infoboard-payload.json" --json
# {"rev":19,"added":11,"updated":0,"removed":0,"unchanged":0,"dryRun":false,"dataPath":"…"}
```

拿到结果后 **先看 `rev`**（这里指**正式 apply**；dry-run 的 `rev` 是不会变的）：`rev` 变成了 `a → b` 就说明真的写了盘 —— 哪怕 `added` / `updated` / `removed` 全是 0（那是勾选升级，见第 4 节）。

真实的一次正式 apply 输出：

```
读取 11 条：新增 11，更新 0，删除 0，未变 0（rev 18 → 19）
```

### 步骤 5：复核

```powershell
infoboard-todo list --json
```

确认 `cx-` 条目数量和 `text` 内容与 cxtodo 一致，且**手写条目（非 `cx-` 前缀）一条都没少**。

> `infoboard-todo list --json` 的结构是 `{"rev": N, "todos": [...]}`，和 cxtodo 的裸数组**不一样**，别搞混。

## 6. 汇报模板

```
学习通 → InfoBoard：新增 N，更新 N，删除 N，未变 N（rev a → b）
最紧的 3 条：<日期> <学科｜标题>（剩 X）
逾期 N 条｜无截止 N 条｜采集于 YYYY-MM-DD HH:MM（N 分钟前）
```

追加要求：

- 有 `stale == true` 的条目 → 单独一行：`注：其中 N 条用的是旧缓存，可能已过期或不完整`。
- 有 `source == "remain"` 的条目 → 单独一行：`注：其中 N 条截止时间是按平台"剩余X天"推算的，可能不准`。
- 本次触发过采集 → 单独一行：`本次触发了采集（pending），耗时 N 秒`。
- `rev` 变了但 `added` / `updated` / `removed` 都是 0 → 单独一行：`注：本次只把 N 条勾选状态升级为已完成，其它内容未变`。
- **口径刚换成"标题在前"之后的第一轮** → 单独一行：`注：本次 11 条均为文本口径升级（text 变更），不是新增作业`。
- "剩 X" 按 `deadline 日期 - 今天` 算天数；无截止时间的不参与排序，单独计数。

⚠️ **排序口径别混用**：InfoBoard 的列表顺序是**"未完成在前 → 有截止的按截止日期升序 → 无截止的按 `createdAt` 倒序"**（即无截止的那一组整体排在所有有截止的之后，但**组内是新的在上**），和 cxtodo 的"按学科分组、组内按最紧截止时间"**不是一回事**。汇报"最紧的 3 条"请统一用**截止时间升序**这一个口径，不要把 cxtodo 的分组顺序当成时间顺序。

---

## 7. 边界与坑

1. **截止时间被"日粒度化"，逾期判断会变宽松。**
   cxtodo 的 `2026-11-14T13:23:00` 进 InfoBoard 后只剩 `2026-11-14`，InfoBoard 认为"当天 23:59:59.999 前都不算逾期"。所以**真实 13:23 已过的作业，在 InfoBoard 里看不出逾期**。需要精确到时刻的逾期判断，请看 cxtodo 的 `bucket`，别依赖 InfoBoard。

2. **`source == "remain"` 的截止时间是推算的，可能本来就错。**
   同步后 InfoBoard 里**看不出来**这条是推算的（InfoBoard 没有 `source` 字段），所以必须在汇报里单独点出来。想更准就用 `python run.py list` 的人类可读模式，它会给这类时间加 `≈`。

3. **重复条目：联动不会识别你手写的同一条作业。**
   如果你之前用 `infoboard-todo add` 为同一份作业手建过条目（id 不是 `cx-` 开头），联动既不会合并也不会去重，会出现两条。**正确处理是删掉手写那条**，而不是去改联动的 id。

4. **勾选与 prune 的交互，容易吓人一跳。**
   你在 InfoBoard 里把某条 `cx-*` 勾成已完成（`completed: true`）：
   - 下次 `apply` **不会**把它取消勾选（`completed` 只升不降）；
   - 但如果这条在学习通里已经交了，它会从 `list` 里消失，于是被 `--prune` **连条目带勾选记录一起删掉**。
     也就是说"勾选"不是永久的保留手段；要长期保留就改成手写条目（但那样就和联动脱钩了）。

5. **手改 `cx-*` 条目的文本/截止时间，下次同步会被覆盖。**
   `apply` 是"整表对齐"语义：来源（cxtodo）说什么，InfoBoard 里就是什么。你在 InfoBoard 里给某条 `cx-*` 改的名字、手动加的截止日期，**下一轮 apply 就没了**，会被 cxtodo 的值盖回去。唯一例外是 `completed` 的勾选（只升不降，会保留，见第 4 节）。想长期保留自己的改法，只能改成非 `cx-` 的手写条目（那样就和联动脱钩了）。

6. **来源这次不给 `deadline`，会把已有的截止时间清掉。**
   payload 条目**省略 `deadline` 字段 = 明确要求"这条没有截止时间"**，不是"别动它"。
   - 本机 cxtodo 就有 2 条（工业化学 `6-7周作业` / `8-9周作业`）是无截止的，所以它们的 payload 里本来就没有 `deadline`；
   - 如果它们后来被 `deadlines.json` 记忆库学出截止时间，下一轮会**自动补上** —— 这是正常现象，不是 bug；
   - 但反过来，**你在 InfoBoard 里给某条 `cx-*` 手填的截止时间，下一轮会被清回空**。所以不要给联动条目手填截止时间。

7. **`list` 无快照时会自动联网同步（~20 秒）。**
   自动化里第一次跑会卡 20 秒，别当成卡死。先用 `doctor` 和 `data\state.json` 是否存在判断。

8. **登录态失效（cxtodo 退出码 2）时不要重试刷屏。**
   直接告诉用户"打开学习通客户端重新登录一次"，然后停。重试只会连续失败。

9. **`--fast` 模式发现不了新交的作业。**
   用户说"刷新"时用 `sync --pending`（默认选择），不要图快用 `--fast`，否则刚交掉的作业还会留在列表里。

10. **`apply` 不是"全量覆盖"。**
    payload 的 `prune` 和命令行 `--prune` **两处都没给**时才绝不删任何东西；给了就只删"以该前缀开头、且本次 items 里没有"的条目。所以手写待办（非 `cx-`）在任何情况下都不会被联动删掉。

11. **`rev` 是最可靠的"有没有写盘"信号（但只在正式 apply 时有效）。**
    - 无变化时 `apply` 不写盘、`rev` 不变：实测再跑一次输出 `没有变化（rev 19 不变）`，`todo.json` **SHA256 一字节未变**；
    - ⚠️ 但反过来**不成立**：`rev` 变了**不代表内容有变化**。勾选升级（某条 `completed` 从 `false` 升到 `true`）会写盘、会 `rev` +1，而计数里仍然显示"未变"。所以**判断有没有写盘只看 `rev`，不要看"未变 N"**；
    - ⚠️ **`--dry-run` 不适用这一条**：dry-run 只会显示 `（rev N 不变）`，永远不写 `a → b`。别用 dry-run 的输出推断 rev 会不会涨。

12. **勾选一条会让它"立刻沉底"，界面自动化别按行号点。**
    已完成条目排在所有未完成之后，所以**你在界面上勾掉任意一条，它的位置会立刻跳到最底部**，它下面的所有行都会上移一格。任何"按行号 / 固定坐标"的点击脚本都会**点错行**。正确做法：
    - 按**文本**定位（而不是序号）；
    - 视口外的行先 `scrollIntoView` 再点，别对着滚出屏幕的坐标下手。

13. **"无截止的排在最后"是错的说法，别拿它做顺序假设。**
    准确规则是：**未完成在前 → 有截止的按截止日期升序 → 都没有截止的按 `createdAt` 倒序**。也就是说无截止的那一组整体在所有有截止之后，但**组内是"新的在上"**。
    实测：11 条 `cx-` 里那 2 条无截止的（工业化学 `6-7周作业` / `8-9周作业`，`createdAt` 是本次同步时刻）排在 4 条手写待办**前面**，就因为它们更新；4 条手写待办之间才是老的在下。所以新同步进来的无截止条目会**插在手写待办上方**，不会沉到最底。

## 8. 回滚：一键清掉所有联动条目

只删 `cx-` 前缀的条目，**不碰任何手写待办**。

PowerShell：

```powershell
'{"items":[],"prune":["cx-"]}' | infoboard-todo apply
```

cmd：

```cmd
echo {"items":[],"prune":["cx-"]}| infoboard-todo apply
```

想先看会删几条，加 `--dry-run`：

```powershell
'{"items":[],"prune":["cx-"]}' | infoboard-todo apply --dry-run
```

- ❌ **不要修改 `C:\Users\30993\Desktop\cxtodo\` 下任何文件**（包括 `data\` 里的 `state.json` / `marks.json` / `config.json`）。cxtodo 不是本项目的一部分，只读使用。
- ❌ **不要在 cxtodo 目录里做 `git init` / `git commit`。** 它不是 git 仓库，也不应该变成 git 仓库。
- ❌ **不要在用户没要求时跑 `sync`**（联网 + 20~80 秒）。
- ❌ **不要跳过 `--dry-run`**。
- ❌ **不要伪造汇报。** 没跑的命令不要说跑过；`apply` 失败就报失败和退出码。
